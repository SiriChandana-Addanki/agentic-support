# Architecture
`TicketContext → Retriever → Planner interface → ActionPlan → PolicyEngine → PolicyDecision → Tools → ToolResult → Resolution` is the execution boundary. `Planner` has deterministic and LLM implementations; deterministic is the default. `LLMPlanner` sees typed retrieval evidence and allowlisted ticket-owned context facts. It has no Store or tool reference. Planner output is strictly parsed and semantically checked before policy or tools. It proposes actions and does not execute or authorize them. Policy independently applies business rules; tools receive `ToolContext`, not raw planner authority, and validate ownership, account status, lifecycle, dates, evidence, stock, serviceability, idempotency, and action-specific transitions.

Duplicate cancellation reads the customer's orders, confirms matching processing orders, and targets only the later one. The cancellation tool independently rejects a duplicate-target request unless another matching processing order exists and the target sorts as later. Already-cancelled requests read status and perform no write. Repeated order-read failures retry to a bounded limit then create an escalation; an expected malformed read can recover on retry. Cancellation timeout recovery re-reads state before deciding whether to retry.

The evaluator is fixture-specific by design, but its state logic uses action and state invariants rather than ticket IDs. Stability fingerprints include final state. Failed write attempts do not count as duplicate successful mutations. Provider errors fall back to the deterministic planner; invalid model output gets one retry, then a locally constructed, validated escalation plan passes through PolicyEngine. No tool runs for an unvalidated model plan. The API remains development-only and unauthenticated. Traces contain planner/provider/model IDs, validation/retry/latency/token metadata, proposed and authorized actions, and executed tools, but never raw prompts, raw model output, or secrets. This repository does not claim production readiness, semantic RAG, or production authentication.

The LLM planner receives allowlisted account status, selected owned-order facts, owned-order summaries only when no order is selected, and replacement stock state. Locked unverified accounts receive no order details and a reduced action catalog. Retrieval emits rule IDs/titles and concise excerpts. Tool purpose, parameters, read/write mode, prerequisites, and avoid conditions come from the shared tool definitions used by the ActionPlan JSON schema. Ordered invocation tuples are executed sequentially. A bounded semantic-completeness check can return one corrective validation message, but PolicyEngine and tool checks remain authoritative.
