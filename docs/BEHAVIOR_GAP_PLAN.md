## Evaluator/planner/tool audit notes

The current evaluator contains hard-coded ticket IDs in `_state`, treats any `ValueError` as invalid tool parameters (including the expected malformed-response injection), and classifies any correct action with a failed state assertion as an evaluator bug. The classification is not evidence by itself: each alleged defect must be validated against the independent plan and observed trace. The ticket-state shortcuts must be replaced by declarative fixture assertions that do not change runtime behavior.

Current distinct planner candidate: unknown refund exception planning (T016). Current tool candidate: malformed read retry handling (T034) requires inspecting result validation/retry semantics; injected malformed output itself is expected and must not be scored as an invalid parameter. The repeated service outage in T031 is a runtime escalation gap, not a reason to ignore the failed escalation criterion.

## Transition contract

Supported transitions from the current data model: `processing → cancelled`; `delivered → return_pickup_scheduled` (return request); pickup reschedule counter `0 → 1`; replacement marker `absent → yes`; payment-link marker `absent/no → yes`; address pincode old → serviceable new; redelivery date absent → requested date. Refund is not directly issued. Any process lacking a current representation must be documented before adding the smallest state field needed.

## Audit disposition (2026-10-04)

The 48 initial rows were not 48 different capabilities: they were 16 ticket scenarios repeated three times. Their groups above were implemented through shared category/policy/tool paths. T016 was the distinct planner behavior gap; T031/T034 were initially misclassified by evaluator heuristics. Re-evaluation now passes 114/114 rows across 38/38 stable tickets. The score is a fixture result and does not establish general or production correctness.

Completed gaps include policy evidence reads and safe policy denial; return-window/non-returnable/high-value outcomes; shipped cancellation alternatives; logistics escalation; address review; refund SLA escalation; payment conflict escalation; suspended and locked-account protections; unknown-process and unavailable-evidence escalation; malformed response retry; and order-service failure escalation. Explicit stateful capabilities include cancellation, return initiation/pickup, payment-link creation, address update, replacement, redelivery, and pickup reschedule, subject to tool-side checks.

Duplicate cancellation now reads customer orders, confirms a matching later processing order, and independently validates the target in the write tool. The earlier duplicate remains processing. Already-cancelled status reads the order, reports only the recorded refund status, and performs no write. Neither flow is selected by ticket ID.

Remaining system limitations: all state is in-memory and reloaded from fixture CSVs; identity is a development principal, not production authentication; attachment filenames are not image evidence inspection; serviceability is a fixed local list; lexical retrieval can return no evidence; there is no carrier integration, persistence, cloud infrastructure, vector retrieval, direct refund tool, or LLM planner. The test set does not establish coverage of every business-rule boundary.
